# RW-181 Plan the Ultralytics importer as SOLID bricks beside the Darknet importer

The row of this entry is in `docs/backlog/MODEL_IMPORT.md`. This file holds what did not fit the row.

- State: open
- Done when: A MODEL_IMPORT design page names the bricks, what they share with the Darknet importer and how a .pt is read; the owner has approved it
- Source: `docs/design/MODEL_IMPORT/README.md`

The owner asked for this plan on 2026-11-15. Its inputs, as given:

- YOLO26n comes first, since it is the industry standard; RW-182 carries it out and RW-183 adds YOLOv5n, YOLOv8n and YOLO11n after it.
- The importer is a command beside `sa import darknet`, built in parallel to it and shaped as it is: one brick per responsibility, each replaceable alone.
- Each brick follows the SOLID shape of `modules/vision/importers`; whatever the two importers share (the model file writer, the weight file writer, the parity check helpers) moves to one place and neither importer copies it.

What the plan has to settle, each a ruling of the owner:

- How a `.pt` is read: natively (a zip reader and a restricted pickle reader in C++, no new dependency) or through a converter script that writes a neutral file (`tools/reference/export_yolo26_reference.py` is one, RW-74).
- Where the Ultralytics layer names map to the rows of `applications/examples/yolo26/model.json`, and which brick owns that table.
- How the import is checked: the same `sa inference` run on coco128 against Ultralytics' own output, with a bound measured the way the Darknet parity suites measure theirs.

Today there is no weight for YOLOv5n, YOLOv8n, YOLO11n or YOLO26n on the machine apart from short runs of `sa train` in `build/`.
