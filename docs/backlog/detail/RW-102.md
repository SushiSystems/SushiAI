# RW-102 Close the step time against Darknet

The row of this entry is in `docs/backlog/MEMORY_PLANNING_SPEED.md`. This file holds what did not fit the row.

- State: open
- Done when: a full-size step takes the time of a Darknet iteration on the same card

## Measured on 2026-11-25

RTX 3080 Ti held at 75 % power by MSI Afterburner (`nvidia-smi` still reports the 350 W default),
YOLOv4 from `yolov4.cfg` at 608 by 608, batch 2, coco128, release build at `7929f99d` without
`--distributed`. The figures of 2026-10-13 (0.76 s against 0.21 s) were taken by a method no file
records, and they do not hold on this card.

| Run | Step |
| --- | --- |
| Darknet, `build_cuda` (CUDA, no cuDNN, no OpenCV), `mosaic=0`, `random=0`, steps 10 to 200 of 256 | 0.351 s and 0.324 s median, two runs |
| SushiAI, 1 epoch against 4 epochs: (1490.07 s - 349.00 s) / 192 steps | 5.9 s |
| SushiAI, `--profile`, 20 steps after 3 warm-up | 4.52 s median in `Runtime`, 4.43 to 4.80 s, cv 2.4 % |

One SushiAI step is about 15 times a Darknet iteration. Darknet's iterations after 200 took 0.8 s
in the first run and 0.33 s in the second; the cause was not looked for.

### Where a step goes

The profile's `breakdown`: `Runtime` 94.2 %, `host` 204 ms (4.3 %), `data` 72 ms (1.5 %), the rest
under a millisecond. One step submits 5302 tasks through the scheduler (`dispatch.task`). Their
device spans run one after another at a median of 724 us each, 5.47 s together, with 0.48 s of
gaps; a `scal` of 256 floats takes 660 us, a copy of 17.7 MB runs at 2.7 GB/s and a GEMM at 0.6
TFLOP/s. `dispatch.submit` holds 8.97 s over the 5302 tasks, 1.7 ms of host time per submit,
summed over the scheduler's workers.

### What was ruled out

SushiRuntime's `Benchmark_ResidencyKernelCost` (`tests/surface/profiling/`) times a chain of
kernels, one buffer per node, on the same card:

| Row | us per node |
| --- | --- |
| 256 floats, `Device` / `Shared`, chain layer | 6.2 / 6.2 |
| 256 floats, `Shared`, host readback after each run | 6.2 |
| 2^22 floats, `Device` / `Shared` | 43.8 / 43.9 |
| 256 floats, `Device` / `Shared`, scheduler | 13.6 / 13.5 |
| 256 floats, `Shared`, 5000 nodes, scheduler / chain layer | 14.9 / 6.4 |

SushiBLAS's `benchmark_level1` records and runs one operation of 256 elements in about 24 us.

So `Residency::Shared` costs nothing next to `Device` on this card, the per-node cost does not grow
with the chain's length, and neither library alone costs 0.7 ms a kernel. The causes this entry
named before (host residency for the heads and deltas, batch normalisation unfused, the deltas on
the host) do not account for 15 times either: a fused kernel removes kernels, but each still costs
0.7 ms while the cause stands.

Neither does the scheduler's idle sleep: `worker_threads.cpp` with `sleep_for(100 us)` replaced by
`yield()` gave a `Runtime` median of 6.31 s against 4.52 s, and the change was reverted.

### The cause: a kernel launch after the host writes managed memory

Nsight Systems 2024.4.2 (`nsys profile -t cuda`, run elevated) over 23 steps on 46 images:

| CUDA call or work | Calls | Total | Median |
| --- | --- | --- | --- |
| `cuLaunchKernel` | 119 370 | 89.6 s (72.5 % of API time) | 695 us |
| `cuEventSynchronize` | 144 730 | 27.4 s | 0.4 us |
| `cuMemAllocManaged` | 1 437 | 0.57 s | 9 us |
| Device kernels, all | 119 370 | 31.2 s, about 1.4 s a step | |

The launch call itself takes 0.7 ms; the device runs about 1.4 s of a 4.5 s step. GEMM is 67 % of
the device time (`gemm_local_tiled` 48.6 %, `gemm_depth_split` 18.1 %), then `Launch::map` 9.2 %,
`im2col` 5.7 %, `col2im` 5.4 %, `reduce_segments` 5.3 %, `channel_affine` 5.3 %.

`Benchmark_ResidencyKernelCost` reproduces the launch cost once the host writes `Shared` memory that
no kernel of the chain touches (256 floats, 100 nodes, chain layer, the run alone timed):

| Row | us per node |
| --- | --- |
| `Shared`, a 2 GiB idle buffer | 7.1 |
| `Shared`, a 2 GiB idle buffer the host writes once per 64 KiB after each run | 5481 |
| `Shared`, 1500 idle buffers of 1 MiB | 7.7 |
| `Shared`, the same, written by the host after each run | 4166 |
| `Device`, the same 1500 buffers | 9.1 |

On this Windows (WDDM) driver, `malloc_shared` is CUDA managed memory without concurrent access: once
the host has written managed memory, every launch that follows pays for it, not only the first.
SushiAI allocates every tensor `Residency::Shared` (`modules/core/allocation/source/allocation.cpp`)
and writes some of them from the host each step (the feed, the targets, the readback), so all
5302 launches of a step pay.

### After device residency

`docs/agent/2026_11_25_DEVICE_RESIDENCY/PLAN.md` and `2026_11_25_DISTRIBUTED_RESIDENCY/PLAN.md`
moved every tensor kernels alone address to `Residency::Device` and the few the host writes each
step to `Residency::Host`; every other host access is a copy through `host_copy.hpp`. The same
profile, same card and cap:

| Group | Before | After |
| --- | --- | --- |
| `Runtime` median | 4.52 s | 0.439 s (0.428 to 0.537 s) |
| `data` | 72 ms | 19.6 ms |
| `host` | 204 ms | 9.3 ms |

The epoch's loss is the same to the printed digits (56.679167, box 49.064717). A step is now about
0.47 s against Darknet's 0.33 to 0.35 s, 1.4 times.
